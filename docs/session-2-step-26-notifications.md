## Цель

Реализовать уведомления внутри приложения (in-app + бейдж) и push (FCM на mobile, web push),
покрывающие все типы из ТЗ §5.8. Уведомления создаются Cloud Functions по событиям системы,
хранятся в коллекции `notifications`, доставляются через FCM по зарегистрированным токенам;
пользователь настраивает типы уведомлений. Соответствие ТЗ §5.8, §9 (п. 11 «Создание
уведомлений»), §7.

## Действия

1. **Фича `notifications`**: модель `AppNotification` (freezed, шаг 4) с полями `type`,
   `title`, `body`, `payload` (ссылки на сущность — курс/задание/квиз/оценку), `isRead`,
   `createdAt`; репозиторий поверх `firestoreProvider` (шаг 2) на чтение своих уведомлений и
   пометку прочитанным; провайдеры `@riverpod` (шаг 4); ошибки → `Failure` (шаг 4).
2. **Тип уведомления** — enum по ТЗ §5.8 (новый курс, новая неделя, новое задание, новый
   квиз, приближение дедлайна, просроченный дедлайн, выставлена оценка, задание возвращено
   на доработку, комментарий преподавателя, системное уведомление администратора).
3. **Cloud Functions — создание уведомлений** (шаг 10, `functions/src/notifications/`,
   ТЗ §9 п. 11): триггеры на событиях создают документы в `notifications` — публикация
   курса/недели/задания/квиза, выставление оценки (шаг 19), возврат задания, комментарий;
   плюс запланированная функция на приближение/просрочку дедлайна.
4. **Экран уведомлений in-app** (раздел из шага 9): список уведомлений пользователя,
   разделение прочитанные/непрочитанные, переход к связанной сущности по `payload`; пустое
   состояние — `AppEmptyView` (шаг 5), UI-кит (шаг 5).
5. **Бейдж непрочитанных**: счётчик в навигации (шаг 9) от стрима непрочитанных уведомлений.
6. **FCM push**: интеграция Firebase Cloud Messaging — обработка foreground/background на
   mobile, **web push** через Service Worker; CF после создания уведомления отправляет push
   по токенам адресата, если канал разрешён настройками.
7. **Регистрация FCM-токена**: получение и сохранение токена устройства в профиле/подколлекции
   пользователя при входе и его обновление; удаление при выходе (шаг 7, `signOut`).
8. **Настройки типов уведомлений** (ТЗ §5.8): экран настроек, где пользователь включает/
   выключает типы и каналы (in-app / push / web push); CF учитывает настройки перед отправкой.

## Типы уведомлений (ТЗ §5.8)

| Тип | Триггер | Канал |
|-----|---------|-------|
| Новый курс | назначение/публикация курса группе студента (шаг 14/16) | in-app + push |
| Новая неделя | публикация недели курса (шаг 14) | in-app + push |
| Новое задание | публикация задания (шаг 17) | in-app + push |
| Новый квиз | публикация квиза (шаг 22) | in-app + push |
| Приближение дедлайна | запланированная CF до `deadline` задания/квиза | in-app + push |
| Просроченный дедлайн | запланированная CF после `deadline` без отправки | in-app + push |
| Выставлена оценка | запись/изменение `grades` (шаг 19), результат квиза (шаг 24) | in-app + push |
| Задание возвращено на доработку | смена статуса отправки на «возвращено» (шаг 19) | in-app + push |
| Комментарий преподавателя | комментарий к отправке/оценке (шаг 19) | in-app + push |
| Системное уведомление администратора | действие админа (шаг 11/12) | in-app + push |

> Каналы фактической доставки фильтруются по настройкам пользователя (in-app / push / web push).

## Решения

- **Создание уведомлений только в Cloud Functions** (ТЗ §9 п. 11), а не на клиенте — клиент
  не может разослать чужие уведомления; это согласуется с правилами шага 27 (запись в
  `notifications` доступна серверу, чтение — владельцу).
- **Единая модель `AppNotification` с типизированным `payload`** — один экран и одна логика
  навигации для всех типов; новый тип добавляется значением enum без переделки UI.
- **Раздельные каналы in-app и push** — in-app работает всегда (Firestore-стрим), push зависит
  от разрешения и токена; настройки §5.8 фильтруют доставку по типу и каналу.
- **Токен в подколлекции пользователя** — поддержка нескольких устройств; протухшие токены
  чистятся при ошибке отправки.
- **Запланированные функции для дедлайнов** — приближение/просрочка не привязаны к событию
  записи, поэтому считаются по расписанию (scheduled CF).

## Артефакты

`lib/features/notifications/domain/` (`app_notification.dart`, `notification_type.dart`,
`notification_settings.dart` — freezed),
`lib/features/notifications/data/` (`notifications_repository.dart`, `fcm_token_service.dart`,
`push_service.dart`),
`lib/features/notifications/presentation/` (`notifications_screen.dart`,
`notification_badge.dart`, `notification_settings_screen.dart`),
`functions/src/notifications/` (триггеры создания уведомлений, scheduled-дедлайны, отправка
FCM с учётом настроек),
web Service Worker для web push,
`test/...` (unit-тесты формирования уведомлений и фильтрации по настройкам).

## Готово, когда

Все типы уведомлений §5.8 создаются Cloud Functions по событиям и приходят in-app; бейдж
показывает число непрочитанных; push доставляется на mobile и web при разрешении пользователя;
FCM-токен регистрируется при входе и снимается при выходе; настройки типов/каналов учитываются
при отправке; уведомления создаются только сервером (не клиентом); unit-тесты формирования
и фильтрации зелёные; `dart analyze` чисто.
