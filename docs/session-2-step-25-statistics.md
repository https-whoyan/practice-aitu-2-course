## Цель

Дать студенту личную статистику, преподавателю — статистику по группам и курсам с
мониторингом и индикатором риска, администратору — общие сводки. Все агрегаты считаются
сервером и хранятся в денормализованных **summary-документах**, которые обновляются Cloud
Functions по событиям; клиент читает готовые сводки, а не тысячи детальных документов
(риск №3 в [`plan-overview.md`](plan-overview.md)). Соответствие ТЗ §5.3.6, §5.6.5, §5.7,
§9, §10.

## Действия

1. **Фича `statistics`**: модели сводок (freezed, шаг 4) — `StudentSummary`,
   `GroupSummary`, `CourseSummary`; репозиторий поверх `firestoreProvider` (шаг 2) только на
   **чтение** summary-документов; провайдеры `@riverpod` (шаг 4); ошибки → `Failure` (шаг 4).
2. **Summary-документы** (денормализация, ТЗ §10): отдельные коллекции/документы по студенту,
   группе и курсу с предрассчитанными метриками (средний балл, % выполнения, просрочки,
   динамика по неделям). Детальные данные (`grades`, `quizAttempts`, `submissions`) и краткие
   summary хранятся **раздельно** (ТЗ §10, п. 5).
3. **Cloud Functions пересчёта** (шаг 10, `functions/src/stats/`): триггеры на событиях —
   запись/изменение оценки (шаг 19), завершение попытки квиза (шаг 24), отправка задания
   (шаг 18). Функция инкрементально обновляет соответствующие summary (ТЗ §9: расчёт
   статистики курса/группы; §10, п. 4 «агрегированные документы статистики»).
4. **Экран статистики студента** (ТЗ §5.6.5): средний % выполнения по курсам, выполненные/
   просроченные задания, пройденные квизы, средний балл, общий прогресс, оценки по неделям,
   динамика, ближайшие дедлайны, рекомендации по незавершённым активностям.
5. **Экраны статистики группы и курса** (ТЗ §5.7.1–5.7.2): средний балл, % выполнения,
   рейтинг студентов, список в зоне риска, динамика по неделям, активность; для курса —
   самые сложные вопросы, задания с просрочками, недели с низкой активностью.
6. **Мониторинг студентов** (ТЗ §5.7.3): карточка студента с курсами, оценками, последней
   активностью и **индикатором риска** низкой успеваемости.
7. **Индикатор риска** (ТЗ §5.7.3): расчёт на сервере по факторам — просроченные задания,
   низкие оценки, непройденные квизы, длительное отсутствие активности, резкое снижение
   результатов; уровень риска кладётся в `StudentSummary`.
8. **Наполнение dashboard'ов**: заглушки секций dashboard'ов (шаг 9) заменяются реальными
   данными из summary; пустые состояния — `AppEmptyView` (шаг 5), UI-кит (шаг 5).
9. **Индексы Firestore** (ТЗ §10) для запросов summary (по группе/курсу/студенту) —
   фиксируются в `firestore.indexes.json`, финально проверяются в шаге 28.

## Источники статистики

| Метрика | Источник | Как считается |
|---------|----------|---------------|
| Средний % выполнения по курсам (студент) | `submissions`, `assignments` | доля сданных в срок от назначенных, агрегируется CF в `StudentSummary` |
| Выполненные / просроченные задания | `submissions` + `deadline` заданий | счётчики обновляются CF при отправке/наступлении дедлайна |
| Пройденные квизы, средний балл по квизам | `quizAttempts` (шаг 24) | CF суммирует завершённые попытки и `score/maxScore` |
| Оценки по неделям, динамика | `grades` (шаг 19) + `courseWeeks` | CF группирует оценки по неделям в `StudentSummary.byWeek` |
| Средний балл группы, % выполнения | `grades`, `submissions` студентов группы | CF агрегирует в `GroupSummary` по членству в группе |
| Рейтинг / зона риска студентов | `StudentSummary` всех членов группы | CF сортирует и помечает по порогам риска (§5.7.3) |
| Самые сложные вопросы квиза | `quizAttempts` (ответы по вопросам) | CF считает долю ошибок по вопросу → `CourseSummary` |
| Задания с просрочками, недели с низкой активностью | `submissions`, `materials`, `quizAttempts` | CF агрегирует по курсу в `CourseSummary` |
| Индикатор риска (§5.7.3) | факторы: просрочки, низкие оценки, непройденные квизы, неактивность | CF считает уровень риска и пишет в `StudentSummary.risk` |
| Общие сводки админа (§5.3.6) | summary-документы + счётчики пользователей/курсов/групп | CF поддерживает системные счётчики (активные пользователи, активные квизы) |

## Решения

- **Денормализованные summary вместо чтения детальных коллекций** — ключевой приём против
  риска №3 (тысячи чтений). Клиент берёт один документ-сводку; пересчёт — на сервере (ТЗ §10).
- **Инкрементальный пересчёт по событиям** (а не полный обход) — CF на триггерах оценок/
  попыток/отправок правят только затронутые поля summary, экономя чтения/записи.
- **Раздельное хранение детальных и summary-данных** (ТЗ §10, п. 5) — детальные документы
  остаются источником истины и пригождаются для аудита, summary оптимизирует чтение.
- **Расчёт риска на сервере** (§5.7.3) — единая логика порогов, недоступная подмене с клиента
  (перекликается с принципом §8.1).
- **Только чтение на клиенте** — репозиторий статистики не пишет summary; запись — исключительно
  через CF, что согласуется с правилами доступа шага 27 (summary доступны на запись только
  серверу).

## Готово, когда

Студент видит личную статистику (§5.6.5), преподаватель — статистику группы и курса с
рейтингом, зоной риска и мониторингом (§5.7), админ — общие сводки (§5.3.6); dashboard'ы
(шаг 9) показывают реальные данные вместо заглушек; индикатор риска считается на сервере по
факторам §5.7.3; статистика читается из summary-документов, а не из детальных коллекций;
unit-тесты агрегаторов и расчёта риска зелёные; `dart analyze` чисто.
