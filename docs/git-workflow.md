# Git-процесс и структура веток

Документ для команды: как устроены ветки, что в них лежит и как с ними работать.

> **Репозиторий для команды:** текущий `origin`
> (`github.com/https-whoyan/practice-aitu-2-course`). Все смотрят сюда.

## Кто за что отвечает

Работа Сессии 1 («Фундамент», ~35% проекта) разбита на три ветки — по человеку.
Деление **3 / 3 / 6** шагов (поровну по объёму кода):

| Ветка       | Владелец  | Шаги Сессии 1                        | Тема                                  |
|-------------|-----------|--------------------------------------|---------------------------------------|
| `yan`       | Yan       | step 1–3                             | Инициализация, Firebase, эмуляторы    |
| `beksultan` | Beksultan | step 4–6                             | Каркас стека/DI, тема и UI, модели    |
| `duran`     | Duran     | step 7–9 + тесты                     | Авторизация, роли/редирект, навигация |

Документация (`docs/`) и презентация ведутся отдельно и в это деление **не входят** —
они лежат на ветке `common`.

## Как устроены ветки (стопка)

Ветки сделаны **стопкой**: каждая следующая ответвляется от предыдущей и включает
её коммиты. Это сделано намеренно — код шагов зависит друг от друга
(один и тот же `lib/routing/app_router.dart`, `pubspec.yaml` и т.д. правятся
на нескольких шагах), и стопка гарантирует **слияние без конфликтов**.

```
4af1764  (база: ТЗ + план разработки)
   │
   ├── yan          = база + step 1–3
   │     │
   │     └── beksultan  = yan + step 4–6           (содержит коммиты yan)
   │           │
   │           └── duran    = beksultan + step 7–9 + тесты   (содержит yan + beksultan)
   │
   └── common       полная история (код + документация) — рабочая ветка-источник
```

Поэтому порядок интеграции строго: **yan → beksultan → duran**.
При слиянии в таком порядке каждое — fast-forward, конфликтов нет.

### Что лежит на каждой ветке (коммиты от базы)

**`yan`** (3 коммита):
```
step 1 — инициализация проекта
step 2 — подключение Firebase
step 3 — Firebase Emulator Suite
```

**`beksultan`** (= yan + 3 коммита):
```
… (3 коммита ветки yan) …
step 4 — каркас стека и DI
step 5 — тема и базовые UI-компоненты
step 6 — модель пользователя и данных
```

**`duran`** (= beksultan + 4 коммита):
```
… (6 коммитов ветки beksultan) …
step 7 — авторизация
step 8 — роли и редирект + Security Rules
test  — идемпотентность тестов Security Rules
step 9 — скелет навигации и dashboard'ы
```

> Код на трёх ветках **идентичен** ветке `common`, за вычетом чисто-документационных
> коммитов (их на `common` отдельно). То есть `duran` = весь код Сессии 1 без `docs/`.

## Инструкция для команды

### 1. Получить свою ветку

```bash
git clone git@github.com:https-whoyan/practice-aitu-2-course.git
cd practice-aitu-2-course

# переключиться на свою ветку (yan / beksultan / duran)
git checkout beksultan
```

На своей ветке ты увидишь весь код вплоть до своих шагов (включая работу
тех, кто «ниже по стопке»).

### 2. Обновляться

```bash
git checkout beksultan
git pull --ff-only origin beksultan
```

Если кто-то «ниже» (например, `yan`) обновил свои шаги — изменения приедут
к тебе через стандартный апдейт стопки (это делает владелец репозитория).

### 3. Запустить проект локально

См. [`dev-runbook.md`](dev-runbook.md): поднять эмуляторы, запустить приложение,
прогнать тесты.

### 4. Порядок интеграции

Сливаем в основную ветку строго по стопке, чтобы не ловить конфликты:

```
yan  →  beksultan  →  duran
```
