## Цель

Преподаватель загружает TXT-файл блочного формата, приложение парсит его, показывает
предпросмотр со списком ошибок (с номерами строк), даёт исправить/пропустить некорректные
вопросы и сохраняет в банк **только после подтверждения** (ТЗ §5.5.10, §17.3). Парсинг и
валидация дублируются: на клиенте — для мгновенного предпросмотра, на сервере (Cloud Function) —
как авторитетная проверка перед batch-записью (ТЗ §9, функции «Импорт вопросов из файла» и
«Валидация вопросов перед сохранением»). Соответствие ТЗ §5.5.10, §5.5.11, §17.3, §9.

## Действия

1. **Парсер блочного TXT-формата** в `features/questions/domain/import/txt_parser.dart` —
   чистая Dart-функция `parse(String) → List<ParsedQuestion>` без зависимостей от Firebase
   (легко тестируется). Разделитель вопросов — пустая строка между блоками; поля —
   `QUESTION`, `TYPE`, `TOPIC`, `DIFFICULTY`, `POINTS`, `OPTIONS`, `ANSWER`, `EXPLANATION`,
   `TAGS`, `PAIRS`, `CATEGORIES`, `ITEMS`, `ORDER` (см. блок «Формат TXT»). Парсер сохраняет
   **номер исходной строки** каждого поля для привязки ошибок.
2. **Модель `ParsedQuestion`** (freezed, шаг 4): распарсенные поля + `sourceLineStart` +
   `List<ImportIssue>` (ошибки/предупреждения с номером строки и кодом). Маппится в `Question`
   (шаг 20) после прохождения валидации.
3. **Валидатор** `features/questions/domain/import/import_validator.dart` — реализует все
   проверки ТЗ §5.5.11 (см. список «Проверки импорта»): наличие текста/типа/ответа, корректность
   типа и баллов, наличие вариантов/пар/категорий под тип, дубли, неполные блоки, ошибки
   форматирования. Возвращает счётчики «найдено / корректно / с ошибками» и список `ImportIssue`.
4. **Экран загрузки** (`/teacher/questions/import`, go_router шаг 9, UI-кит шаг 5): выбор файла
   (`file_picker`), чтение текста, запуск клиентского парсера+валидатора.
5. **Экран предпросмотра**: сводка (найдено/корректно/с ошибками), список вопросов с бейджем
   статуса, раскрытие ошибок с **номером строки**, инлайн-правка каждого вопроса (форма из шага
   20), переключатель «пропустить некорректные», кнопки «Подтвердить импорт» и «Отменить»
   (§5.5.11, §17.3 пп.5–8).
6. **Cloud Function `importQuestions`** в `functions/src/questions/import.ts` (callable):
   принимает массив подтверждённых вопросов, **повторно валидирует на сервере** (та же логика,
   что клиент — §9 функция 7), проверяет `ownerTeacherId == caller` и роль `teacher`, пишет
   `questionBank` **batch-операцией**, возвращает результат. Запись в `auditLogs` (actionType
   `questions.import`, §8.6, §17.3 п.10). Каркас функций — [шаг 10](session-2-step-10-cloud-functions-admin.md).
7. **Контракт вызова** в `features/questions/data/` — метод `importQuestions(...)` поверх
   `functionsProvider` (шаг 2/10), ошибки → `Failure` (шаг 4). Сохранение только после
   подтверждения преподавателем (§5.5.11).
8. **Тесты парсера** (golden-файлы из примеров ТЗ §5.5.10: single, multiple, matching, drag_drop,
   ordering), тесты валидатора на каждый класс ошибок §5.5.11, тест Cloud Function на эмуляторе
   (валидный/невалидный batch, проверка прав).

> В MVP импортируются 4 типа (single / multiple / trueFalse / shortText, шаг 20). Парсер
> распознаёт блоки `PAIRS / CATEGORIES / ITEMS / ORDER` и помечает такие вопросы как
> «тип вне MVP» — это валидное предупреждение, а не ошибка формата.

## Формат TXT (ТЗ §5.5.10)

Один вопрос — блок «ключ: значение», вопросы разделяются пустой строкой. Реальный пример из ТЗ
(вопрос с одним правильным ответом):

```
QUESTION:
What is the main purpose of version control?

TYPE:
single

TOPIC:
Git

DIFFICULTY:
basic

POINTS:
1

OPTIONS:
A) To manage changes in files
B) To compile source code
C) To design user interfaces
D) To host databases

ANSWER:
A

EXPLANATION:
Version control systems track and manage changes in files over time.

TAGS:
git, version-control, basics
```

Вопрос с несколькими ответами — `TYPE: multiple`, `ANSWER: A, B, D`. Вопрос на соответствие —
`TYPE: matching` + блок `PAIRS:` (`Primary key => Unique identifier of a record`). Drag and drop —
`TYPE: drag_drop` + блоки `CATEGORIES:` и `ITEMS:` (`Python => Programming language`). Сортировка —
`TYPE: ordering` + блок `ORDER:` (по одному элементу на строку в правильном порядке).

## Проверки импорта (ТЗ §5.5.11)

Валидатор проверяет каждый блок:

1. Наличие текста вопроса (`QUESTION`).
2. Наличие типа вопроса (`TYPE`).
3. Корректность типа (значение из `QuestionType`, шаг 20).
4. Наличие правильного ответа (`ANSWER` / `PAIRS` / `ORDER` под тип).
5. Наличие вариантов (`OPTIONS`) для вопросов с выбором.
6. Наличие пар (`PAIRS`) для `matching`.
7. Наличие категорий (`CATEGORIES`/`ITEMS`) для `drag_drop`.
8. Корректность баллов (`POINTS` — положительное число).
9. Корректность темы (`TOPIC` непустая).
10. Повторяющиеся вопросы (дубли по тексту+типу).
11. Неполные блоки (отсутствует обязательное поле).
12. Ошибки форматирования (нераспознанный ключ, битый разделитель, `ANSWER` вне диапазона
    `OPTIONS`).

После проверки предпросмотр показывает (ТЗ §5.5.11): количество найденных вопросов, количество
корректных, количество с ошибками, список ошибок, **номер строки** каждой ошибки, предпросмотр
каждого вопроса, правку до сохранения, пропуск некорректных, отмену импорта.

## Решения

- **Двойная валидация (клиент + Cloud Function)**: клиент даёт мгновенный предпросмотр с
  номерами строк, сервер — авторитетная проверка перед записью (§8.1, §9 функция 7); общая логика
  правил вынесена так, чтобы не разъезжалась.
- **Парсер — чистая функция без Firebase** — тестируется golden-файлами из примеров ТЗ §5.5.10,
  не требует эмулятора.
- **Хранение `sourceLineStart`** в `ParsedQuestion` — без него невозможен пункт §5.5.11
  «номер строки с ошибкой».
- **Batch-запись в Cloud Function**, а не по одному документу с клиента — атомарность импорта,
  серверная проверка прав (`ownerTeacherId`, роль) и единая запись в `auditLogs` (§8.6).
- **«Тип вне MVP» — предупреждение, а не ошибка** — файл с `matching`/`ordering` парсится
  корректно; такие вопросы можно пропустить, не блокируя импорт остальных.
- **Сохранение только после подтверждения** (§5.5.11) — никакой записи на этапе предпросмотра.

## Готово, когда

Загрузка примера из ТЗ §5.5.10 даёт корректный предпросмотр; ошибочные блоки помечены с верными
номерами строк по всем 12 проверкам §5.5.11; преподаватель правит/пропускает некорректные и
подтверждает; Cloud Function повторно валидирует, проверяет права и пишет `questionBank` batch'ем
+ запись в `auditLogs`; без подтверждения в базу ничего не попадает; `dart analyze` чисто,
тесты парсера/валидатора и тест функции на эмуляторе зелёные.
