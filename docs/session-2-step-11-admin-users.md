## Цель

Собрать административный раздел управления пользователями: списки преподавателей и студентов с
пагинацией, фильтрами и поиском, карточку пользователя и формы создания/редактирования. Чтение
идёт напрямую из `users`+`profiles`, а все мутации (создание, смена роли, блокировка, мягкое
удаление) — через Cloud Functions шага 10, а не записью с клиента (ТЗ §8.1). Соответствие ТЗ
§5.3.1–5.3.3, §5.2, §14.2, §10.

## Действия

1. **Фича `admin`** с папками `data/domain/presentation` под `lib/features/admin/` (стандарт из
   шага 4); раздел открывается под ролевым shell'ом `/admin` (шаг 9), защищён `requireRole({admin})`
   (шаг 8).
2. **`AdminUserRepository`** (контракт в `domain/`, реализация в `data/` поверх
   `firestoreProvider`, шаг 2): чтение `users`+`profiles` (шаг 6); список с **пагинацией**
   (`startAfter`/`limit`, ТЗ §10) и фильтрами по роли, статусу, группе, курсу; **поиск** по имени
   и email через префиксные запросы (`>=`/`<` по нормализованному полю — учитывает риск №2 из
   plan-overview про индексы); ошибки → `Failure` (шаг 4).
3. **Riverpod-провайдеры** (`@riverpod`, code-gen): `adminUsersProvider` (постранично, с
   параметрами фильтра/поиска), `adminUserProvider(uid)` (карточка), `adminUserFiltersProvider`
   (состояние фильтров/поиска).
4. **Вызовы Cloud Functions** (шаг 10) из `data/`: `createUser`/`createTeacher`, `setUserRole`,
   `blockUser`/`unblockUser`, `softDeleteUser` — тонкие клиентские обёртки над callable; UI после
   успеха инвалидирует провайдеры списков.
5. **Экраны** (ТЗ §14.2, UI-кит из шага 5): список пользователей, карточка пользователя,
   создание, редактирование, отдельные списки преподавателей и студентов (фильтрация по роли).
   Пустые/загрузочные/ошибочные состояния — `AppEmptyView`/индикаторы шага 5.
6. **Карточка пользователя** показывает дату регистрации и последнего входа, принадлежность к
   группам и курсам (ТЗ §5.3.1 п.9–10), статус и роль; действия (блок/разблок/смена роли/мягкое
   удаление) — кнопки, дергающие функции шага 10.
7. **Мягкое удаление скрывает из активных списков**: репозиторий по умолчанию фильтрует
   `status != deleted/archived`; для аудита предусмотреть переключатель «показать архивных».
8. **Согласовать UI и права** (ТЗ §8.1): кнопки прячутся для UX, но реальную проверку делает
   `assertAdmin` в функциях (шаг 10) — клиент не пишет в `users` напрямую.

## Экраны (ТЗ §14.2)

| Маршрут | Экран | Назначение |
|---------|-------|-----------|
| `/admin/users` | Список пользователей | Пагинация + фильтры (роль/статус/группа/курс) + поиск |
| `/admin/users/:uid` | Карточка пользователя | Данные, роль, статус, группы/курсы, даты, действия |
| `/admin/users/new` | Создание пользователя | Форма → `createUser` (письмо установки пароля) |
| `/admin/users/:uid/edit` | Редактирование | Правка профиля; смена роли → `setUserRole` |
| `/admin/teachers` | Список преподавателей | Список с фильтром по роли `teacher` (ТЗ §5.3.2) |
| `/admin/students` | Список студентов | Список с фильтром по роли `student` (ТЗ §5.3.3) |

> Все мутации экранов идут через Cloud Functions шага 10. Списки используют пагинацию и поиск из
> `AdminUserRepository` (ТЗ §10).

## Решения

- **Чтение с клиента, запись через функции**: списки/карточки — обычные Firestore-запросы
  (быстро, дёшево), но критичные изменения проходят серверную проверку (ТЗ §8.1, шаг 10) — нельзя
  поднять себе роль запросом из консоли.
- **Пагинация курсором (`startAfter`)**, а не `offset`: ТЗ §10 требует пагинации больших
  списков; курсор не перечитывает пропущенные документы (минимизация чтений §10 п.6).
- **Поиск по префиксу через нормализованное поле** (lower-case `firstName`/`email`): Firestore не
  умеет полнотекст; префиксный диапазон закрывает сценарий §10 п.3 без внешнего движка — отмечен
  как риск индексов №2 в plan-overview, индекс заводится заранее.
- **Списки преподавателей/студентов — один репозиторий с фильтром роли**, а не дублирующий код:
  отличается лишь параметр запроса.
- **Мягкое удаление по умолчанию скрыто, но доступно для аудита**: соответствует §5.3.1 — данные
  сохранены, активные списки чистые, при разборе спорных ситуаций архивных видно.

## Готово, когда

Админ видит постраничные списки пользователей/преподавателей/студентов с работающими фильтрами и
поиском; карточка показывает роль, статус, группы/курсы и даты; создание шлёт письмо установки
пароля, смена роли/блокировка/мягкое удаление отрабатывают через функции шага 10 и обновляют
списки; архивные скрыты из активных списков; `dart analyze` чисто и тесты репозитория проходят.
